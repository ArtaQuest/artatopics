Journal of Seasonality

Author guide & style

Journal of Seasonality runs a fully automated, end-to-end AI review process — there is no human peer review. Your submission is reviewed by running it: the reviewer compiles your manuscript, clones your code, fetches your open data, executes it, and checks that your results actually reproduce — across as many rounds of feedback as it takes. Only work that reproduces is accepted.

1. What you submit

Three public URLs — open data and open code are mandatory; nothing is reviewed on description alone:

ArtefactWhat
ManuscriptA zipped LaTeX project that compiles to a PDF — an Overleaf export or any TeX project. Our class artaquest.cls is recommended, not required.
CodeA public git repository (ideal) or a downloadable archive that runs.
DataA public, downloadable URL for your open data.

2. The LaTeX template

The template is a complete, compiling exemplar built on our document class artaquest.cls — a Times-like, single-column (two-column optional) journal class with a brand-styled masthead, structured title block, numbered clickable references and cleveref cross-references. It uses only common CTAN packages and is self-contained: tectonic main.tex builds it with no TeX install. The bundled main.tex doubles as a worked example — read it, then replace its content with yours.

⬇ Download the template (.zip)
Locally: tectonic main.tex (one binary, fetches packages) — or latexmk -pdf main.tex with a TeX Live install.
On Overleaf: New Project → Upload Project → upload the .zip → Recompile. When you're ready, Menu → Download Source gives you the .zip you submit. Keep artaquest.cls in the project root.
Class options: \documentclass[11pt]{artaquest} (single column, default) · [11pt,review] adds line numbers + double spacing for drafting · [11pt,twocolumn] sets a two-column body. Any article option (a4paper, letterpaper, 12pt…) is passed through.

3. Manuscript structure

A short, honest paper. The usual arc, adapt as needed:

  • Title — a clear, specific statement of the result (no trailing full stop).
  • Authors, affiliations, ORCID — \author{A\affmark{1}\orcid{0000-…} \and B\affmark{2}}, \affiliation{\affmark{1}… \affmark{2}…}.
  • Abstract — what you did, what you found, and the headline numbers that should reproduce; \keywords{…} after it.
  • Introduction · Data · Methods · Results · Discussion — with the limitations and a short reproducibility note stated honestly.
  • Declarations — \declarations prints your Data/Code availability; then author contributions, competing interests, funding.

4. Formatting conventions

The class wires these up for you — use the commands and they come out in house style:

  • Title block — \author{A\affmark{1}\orcid{0000-…} \and B\affmark{2}}, \affiliation{\affmark{1}… \affmark{2}…}, \keywords{…}, optional \runningtitle{…} for the header. \maketitle prints the masthead, a bold gold rule, the large title, the authors (each \orcid{…} renders a small gold “iD” badge linked to ORCID) and the date.
  • Abstract — \begin{abstract}…\end{abstract} sets a roman, slightly-smaller justified lead block between two thin gold rules (roman, not italic — it reads more comfortably over a long abstract), with a blue small-caps “Abstract” run-in head, and prints your \keywords beneath it. Bold a few run-in cues (\textbf{Method:}, \textbf{Headline:}) to structure a longer abstract.
  • Headings — sentence case, no trailing full stop, numbered in brand blue. \paragraph{…} for run-in subpoints.
  • Figures — \includegraphics in a figure; caption below; subcaption for sub-figures. Write normal LaTeX figures for the PDF, but the data behind every figure must be regenerated by your code — see Figures & visualisation.
  • Tables — booktabs rules; no vertical lines; caption above; align numbers with a siunitx S column.
  • Maths — display equations with equation and a \label; define symbols on first use.
  • Cross-references — cleveref: \cref{eq:decomp} → “Equation 1”, \cref{tab:…}, \cref{fig:…}, all clickable in the PDF and in the web reader. Label everything you reference — see §6.
  • Numbers & units — siunitx: \num{521}, \SI{7}{\day}, \SI{63}{\percent}. Consistent significant figures.
  • Code — brand-styled lstlisting for the one command that reproduces your results.
  • Citations — numeric natbib: \citep{key} → [3], \citet{key} → “Harris et al. [3]”. Clickable, with DOIs as links in the reference list — see §6.
  • End-matter — \declarations (prints Data/Code availability) then \authorcontributions{}, \competinginterests{}, \funding{}, \acknowledgements{}.
  • Drafting — \documentclass[11pt,review]{artaquest} numbers lines and double-spaces while you work.
  • Spelling & voice — British spelling; plain, precise prose; no hype.

5. Mathematics

State every model and metric as a typeset equation. If you report a number, give the reader the expression that produces it — the reviewer recomputes exactly what your equation says, not what your prose implies. The class is maths-first: it loads amsmath, amssymb, mathtools and amsthm for you, so you never \usepackage them.

Equations

  • Number what you reference. Use equation with a \label{eq:…}; displays are right-numbered as (1). Reference with \cref{eq:strength} → “Equation 2”. Don’t number throwaway displays you never cite.
  • Multi-line maths: use align (one & alignment point, one number per line) for systems of equations or a definition followed by its expansion. \allowdisplaybreaks is on, so a long derivation breaks across a page cleanly.
  • Inline vs display: short relations stay inline ($F_S \in [0,1]$); anything you name, derive, or point a number at goes on its own numbered line.
  • Define every symbol on first use, and keep notation consistent throughout.

House maths macros

Use these so notation is consistent and upright where it should be (an operator or metric is a name, not a product of letters):

Theorem-like environments

Brand-styled, shared-counter, numbered within the section (a blue run-in head for results, gold for definitions). Reference them with cleveref just like equations.

  • Results: theorem, lemma, proposition, corollary (italic body). Definitions & notes: definition, remark, assumption (upright body).
  • Proofs: \begin{proof}…\end{proof} closes with a gold ∎.
  • Label and cross-reference: \begin{definition}\label{def:strength}… → \cref{def:strength} gives “Definition 3.1”.

6. Visualisation

Read this before you make a single figure. In the published web reader, your figures are not the image files you compiled. The reader renders each figure as the journal's own interactive chart, generated from your reproduced data when the reviewer runs your code. So a figure is only publishable if a clean machine can regenerate the data behind it by running your code.

Two surfaces, one source of truth:

  • In the PDF — keep using ordinary LaTeX figures: \includegraphics inside a figure (or draw inline, as the exemplar does), with the \caption below and subcaption for panels. This is what compiles and what a reader downloads.
  • In the web reader — the journal re-plots your figures as native, interactive charts (pan, hover, read-off) built from the data your code emits. Pre-made or uploaded image files are not shown on the web; the reader uses the data, not your raster.

What this means for how you work:

  • Every figure must be reproducible from the code. The reviewer regenerates each one by running your pipeline. A figure that cannot be regenerated by running the code is sent back — a screenshot, a hand-drawn diagram, or a plot whose data isn't produced by the released code will not pass.
  • Emit the data, not just the picture. Have your code write the series behind each figure to a plain, open format (CSV/JSON) as it runs, alongside the rendered .pdf/.png you put in the manuscript. The web chart is built from that data.
  • Make the figure deterministic. Same code + same open data → same figure, every time (seed any randomness; pin versions). A figure that changes run-to-run cannot be reproduced or re-plotted.
  • Caption what the data shows, not how the raster looks. Axes, units, and the quantity plotted should be legible from the data alone, since the web reader redraws it.
  • Schematics (a method diagram with no underlying data) are fine as figures in the PDF; they simply aren't re-plotted on the web. Anything that presents a result, though, must come from the code.

The aq house style for figures

The class loads tikz + pgfplots and defines a reusable axis style. Apply [aq] to every axis and your figure inherits the journal’s look — a light grid, tidy legend, sensible default size, no chartjunk:

\begin{tikzpicture}
  \begin{axis}[aq, xlabel={Week of year}, ylabel={Seasonal $S_t$}, legend pos=north west]
    \addplot[aq emphasis] {…};    % the exemplar / median / "answer" curve
    \addplot[aq warm, dashed] {…}; % a secondary series, in gold
    \addplot[aq muted] {…};      % a muted, dashed comparison
    \addplot[aq rule, samples=2] {0}; % a reference line (baseline / threshold)
    \legend{…, …, …}
  \end{axis}
\end{tikzpicture}
  • Named brand colours: aqgold / aqblue (+ aqgoldlight, aqbluelight, aqgreydark). Two hues only — never a third accent; greys and tints are derived from the two.
  • Per-plot styles you apply to an \addplot: aq emphasis (the median / exemplar / “answer” curve — heavy blue), aq warm (a gold secondary), aq muted (a faint dashed comparison), aq rule (a dashed reference line), and aq band (a translucent confidence band — load \usepgfplotslibrary{fillbetween}, as the exemplar does).
The colour-blind rule: colour is never the only channel. The [aq] cycle list gives every series a distinct colour and line dash and marker. So your figure stays legible printed in greyscale, photocopied, or read by someone with colour-vision deficiency — and on projectors that mangle hue. If you override the cycle, keep all three channels varying. Never distinguish two lines by colour alone.

Choosing the right chart

  • Faithfully show all your data. Prefer charts that reveal the full distribution over ones that hide it. A bar of means conceals spread; show the points.
  • Small distributions → a 1-D dot / strip plot. For a handful of values per group (say n ≲ 30), plot every observation as a dot along one axis (a strip / jitter plot or a Tufte-style dot plot) rather than a bar or a box that erases the individual data. A box plot is for larger samples; for small ones the dots are the summary.
  • Time series → lines (use aq emphasis for the headline series, aq muted for comparisons). Distributions → histograms / dot plots / ECDFs. Relationships → scatter (let the reader see the cloud, not just a fitted line). Comparisons of a few quantities → a dot plot, not a 3-D pie.
  • Reference lines carry meaning. Mark a baseline, a threshold, a target, or a null with an aq rule line and say in the caption what it is — a reader should never have to guess what “the dashed line” means.
  • No chartjunk. No 3-D, no gradient fills, no needless gridlines or drop shadows, no dual y-axes unless genuinely unavoidable. Start a count/magnitude y-axis at zero unless you flag the truncation.

Self-contained captions

  • Caption what the data shows, with units. State the quantity plotted, the axes and their units, what each series is, and what any reference line marks — so the figure reads on its own. Because the web reader redraws the chart from your data, caption the data, not the raster.
  • The class styles captions for you: a bold small-caps “Figure N.” run-in head, hanging indent, justified. Put the \caption below the figure (and above a table). No trailing full stop is fine; a self-contained sentence is better.

7. Referencing & cross-references

Two kinds of links, both clickable in the PDF and in the web reader. Get both right and your paper threads together cleanly.

Citing the literature (numbered)

  • Cite numerically with natbib: \citep{key} → [3] for a parenthetical citation, \citet{key} → “Harris et al. [3]” when the authors are the subject of your sentence. Group several: \citep{a,b,c} → [1–3].
  • Every entry in references.bib must be real and verifiable, and carry a DOI where one exists: add a doi = {10.…} field. The class provides \doi{…}, so the DOI renders as a clickable doi:… link in the reference list. The reviewer checks citations — invented or unverifiable references are grounds for rejection.
  • Build the bibliography with \bibliography{references} at the end; the numbered, DOI-linked reference list is produced for you. Replace the bundled well-known entries with your own.

Cross-referencing your own figures, tables and equations

  • Label everything you point at: \label{fig:decomp}, \label{tab:summary}, \label{eq:strength} (a fig:/tab:/eq: prefix keeps them tidy).
  • Reference with \cref: \cref{fig:decomp} → “Figure 1”, \cref{tab:summary} → “Table 1”, \cref{eq:strength} → “Equation 2”. cleveref supplies the word for you — never hard-code “Figure 1”, or the numbers drift. Use \Cref{…} at the start of a sentence.
  • These become clickable cross-links in the reader — a reader (and the reviewer) can jump straight from the prose to the figure, table or equation it names.

8. Reproducibility — the thing that matters most

The test we apply: a clean machine, given your code and your open data, reproduces the numbers and figures in your abstract. Make that one command.
  • One command or notebook regenerates every figure and number from the open data.
  • Pin dependencies (requirements.txt, environment.yml, lockfile) and say how to run it in a README.
  • The numbers in your abstract must follow from running your code — never hard-coded, mocked, or pre-baked.
  • Data & Code availability statements point at the exact public URLs you submit.

9. How review works

Each round, the reviewer (ArtaScience — Claude at maximum effort, in a sandbox) compiles your LaTeX, reads the manuscript, runs your code on your open data, and compares the outputs to your claims. It returns:

FieldMeaning
reproducedyes/no — a paper that does not reproduce cannot be accepted.
score0–100 overall assessment.
verdictaccept · revise (address the report and resubmit — a fresh round is reviewed) · reject.
reportexactly what was run, what reproduced, what did not, and how to fix it — published verbatim.

On acceptance your manuscript is assigned a permanent DOI (Zenodo/DataCite). Every submission and every round of feedback is public.

10. What gets rejected — and the most common reasons for revision

Rejected outright:

  • Results that don't reproduce, or that are hard-coded/mocked rather than computed.
  • A figure whose data the code does not regenerate — a screenshot, an uploaded image, or a plot the reviewer cannot reproduce (the web reader re-plots figures from your data; see §5).
  • No open code, or no open data — or a manuscript that isn't a compiling LaTeX project.
  • Invented or unverifiable citations, DOIs, or URLs.
  • Causal claims unsupported by the design; hype in place of evidence.

Sent back for revision (these are what the reviewer most often catches — fix them before you submit):

  • Over-claiming reproducibility. Don't say the script “reproduces every number” if it only computes some. State exactly what it regenerates; ship code for anything else you call reproducible.
  • Resting a claim on data you didn't publish. Every quantitative claim must be computable from the open data you submit. If a section needs a private/derived dataset, publish it or scope the claim honestly.
  • A number that doesn't reconcile. The reviewer recomputes your headline figures independently. If a stated bound/threshold doesn't match what the open data gives, correct it.
  • Unpinned dependencies. Pin versions so the run is deterministic; note the environment in your README.

11. Pre-submission checklist

  • The manuscript compiles to a PDF with no errors.
  • Abstract states the headline result and the numbers that should reproduce.
  • Data + Code availability point at the exact public URLs you submit.
  • One command/notebook regenerates every figure and number from the open data.
  • Every figure's underlying data is emitted by the code (CSV/JSON), so the web reader can re-plot it.
  • Every model and metric is stated as a typeset, numbered equation; symbols are defined on first use.
  • Every figure distinguishes its series by colour and dash and marker (the [aq] style does this); captions state axes, units, and what each reference line marks.
  • Every figure, table and equation you reference is labelled and cited with \cref; every citation carries a real DOI where one exists.
  • Dependencies are pinned and the run steps are documented.
  • Every citation, DOI, and URL is real.
